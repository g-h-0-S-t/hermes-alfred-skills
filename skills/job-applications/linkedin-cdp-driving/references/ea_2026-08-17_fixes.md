## 1. "empty_modal" / "no-continue-submit" was a FALSE diagnosis (not a LinkedIn glitch)
- Symptom in logs: `empty_modal` / `no-continue-submit`. The natural conclusion was
  "LinkedIn rendered the modal empty / session throttled."
- VISION PROOF (screenshot + vision_analyze): the modal was FULLY rendered (TCS contact-info
  step 1/4 pre-filled with user's profile; step 2/4 resume already selected with green checkmark).
  Nothing was empty.
- ROOT CAUSE: `document.querySelector('div[role=dialog]')` returns the FIRST `div[role=dialog]`,
  which on LinkedIn is frequently an EMPTY accessibility overlay whose only text is
  "This is a modal window." Scoping field/button scans to that first dialog returned 0, so the
  bot bailed. LinkedIn renders MULTIPLE `div[role=dialog]`.
- FIX: scope all scans to `document` (whole page). For Continue/Submit, search ALL `button`
  elements, prefer `getBoundingClientRect().width>0 && height>0 && !disabled`.
- LESSON: never trust a field-count of 0 to mean "LinkedIn glitched." Vision-confirm first.

## 2. Radio question text = PRECEDING SIBLING of the fieldset (not an ancestor)
- DOM dump of one radio (`role=radio`, text "Yes"):
  - div "Yes" → div "Yes No" → FIELDSET "Yes No" → div "Mandatory hands of experience..." →
    div "How many years of work experience do you have with AWS?* 0/20..." → div "Additional Questions..."
- So the question `<div>` is a PRECEDING SIBLING of the `<fieldset>` containing the radios,
  1-2 siblings back. Climbing PARENT/ancestor nodes never reaches it → "(unlabeled radio)".
- WORKING extractor (in-page):
  ```js
  const fs = r.closest('fieldset') || r.closest('div[role=group]');
  let node = fs || r.parentElement;
  for (let i=0;i<12 && node;i++){
    let sib = node.previousElementSibling;
    while (sib){
      const t=(sib.innerText||'').replace(/\s+/g,' ').replace(/\b(yes|no)\b/gi,'').trim();
      const qi=t.indexOf('?'); if(qi>=0) return t.slice(0,qi+1);
      sib=sib.previousElementSibling;
    }
    node=node.parentElement;
  }
  return '';
  ```

## 4. f_TPR works server-side; posted-time text parsing STARVES the run
- Earlier note: "f_TPR=r18000 silently becomes 24h, parse 'X hours ago' text instead." WRONG.
- Evidence: with `f_TPR=r18000` in the URL, only ~1 relevant card returned per 5h window (correct).
  With the text-parser `ageHours` filter, EVERY card had `posted: "(none)"` (LinkedIn cards show
  "Company review time"/"Applied", not "X hours ago") → ageHours=999 → all skipped → 0 jobs.
- FIX: put `f_TPR=<r18000|r43200|r86400>` in the search URL (let LinkedIn filter by time) and apply
  ONLY a relevance filter on returned cards. Don't parse post-time text for recency.
- Window helper: `TPR = WINDOW_HOURS<=5 ? 'r18000' : (WINDOW_HOURS<=12 ? 'r43200' : 'r86400')`.
